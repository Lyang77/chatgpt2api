# 可用账号归零飞书告警设计

## 目标

当 chatgpt2api 号池的可用账号数变为 `0` 时，通过飞书群自定义机器人发送一条告警。一次连续的归零状态只发送一次；可用账号恢复后仅重置内部状态，不发送恢复通知。

## 告警口径

- 使用 `AccountService.get_stats()["active"]` 作为可用账号数。
- 服务启动后的第一次检查如果已经为 `0`，立即尝试告警。
- 告警成功后，持续为 `0` 时不再重复发送。
- 可用账号恢复为大于 `0` 后重置告警状态；以后再次归零时可以重新告警。
- 告警发送失败时不记录为已发送，下一个账号检查周期继续重试。
- 状态保存在当前进程内。服务重启后如果仍为 `0`，会再发送一次告警。

## 实现位置

新增独立的飞书 Webhook 发送模块和号池归零状态判断模块，避免把 HTTP 请求、告警去重状态直接混入 `AccountService`。

现有 `api.support.start_limited_account_watcher` 已按 `refresh_account_interval_minute` 周期维护账号状态。每轮账号刷新及 refresh token 保活处理结束后，读取最新统计信息并执行一次归零检查。监控线程启动后会立即执行首轮检查，因此无需新增定时线程。

为了让周期行为可以直接测试，将单轮账号维护和告警检查提取为独立函数，后台线程只负责循环调用和等待。

## 飞书消息

- Webhook 地址按用户要求作为源码常量保存，不新增环境变量或设置页面。
- 使用飞书卡片消息格式：`msg_type=interactive`，卡片结构使用 `schema=2.0` 和红色标题栏。
- 卡片只用于提醒告警：显示服务名、`可用账号为 0`、处理提示和北京时间。
- 不展示账号总数、限流数、异常数、禁用数等号池明细。
- 请求设置短超时，并同时校验 HTTP 状态和飞书响应中的业务状态。
- 日志只记录发送结果和错误原因，不打印 Webhook 地址。

## 异常与运行影响

- **触发条件：** 仅当最新统计中的 `active == 0` 时触发；限流、异常、禁用数量变化本身不单独触发。
- **超时风险：** Webhook 请求发生在现有后台监控线程，不占用 API 请求时间；短超时只会延迟本轮后台检查。
- **执行方式：** 后台线程同步发送，无需新增任务表或消息队列。
- **失败补偿：** 发送失败后保留未告警状态，下个检查周期自动重试，并在服务日志记录失败原因。
- **堆积风险：** 不创建异步任务，不累计待发送消息；任意时刻最多只有当前监控线程的一次发送尝试。
- **多进程边界：** 去重状态是进程内状态；若未来同时运行多个应用进程或多个实例，每个实例都可能各发送一次。本次不增加分布式锁或持久化状态。

## 测试范围

- 第一次检查到 `active == 0` 时发送一次。
- 连续多次检查为 `0` 时只发送一次。
- 恢复为大于 `0` 后再次归零时重新发送。
- 恢复时不发送消息。
- Webhook 发送失败后，下次检查继续重试。
- 可用账号始终大于 `0` 时不发送。
- 飞书发送器生成正确的极简告警卡片，并正确处理成功、HTTP 失败、飞书业务失败和网络异常。
- 单轮账号维护结束后使用最新账号统计执行告警检查。

## 不在本次范围内

- 号池恢复通知。
- 前端告警配置页面。
- Webhook 签名校验。
- 告警状态持久化、跨进程去重、发送历史查询和人工重发。
